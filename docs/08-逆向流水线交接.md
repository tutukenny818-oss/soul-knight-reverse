## 一、最重要的结论（新会话必读）

### 1. v1 文档的判断是错的

v1 说「`.so` 被加固，必须从内存 dump」。**实测推翻**：

| v1 判断 | 实测 |
|---|---|
| metadata registration 段被截断 | ❌ ELF 完整，8 个 PT_LOAD 齐全，`.rela.dyn` 1,817,321 条完整 |
| 需要内存 dump 才有完整 `.so` | ❌ 磁盘文件已完整 |
| `ERROR: This file may be protected.` = 加固 | ❌ 只是 `DT_INIT` 存在的提示 |

### 2. 真正的卡点是 5 处（全部已解决）

| # | 卡点 | 解法 |
|---|---|---|
| 1 | `.data.rel.ro` 指针全为 0（等动态链接器填） | 自行应用 `.rela.dyn`：1,815,534 条 RELATIVE + 1,631 条 ABS64 |
| 2 | `.so` 有第二层「周期窗口单字节异或」加密 | `key=0x6F, period=0x10000, window=[0x3000,0x7000)`，范围 `file [0x2D50000, 0x3B50000)` |
| 3 | **`global-metadata.dat` 多张表用紧凑布局**（最关键） | `methods` 36→56 字节，`events` 24→32 字节 |
| 4 | 22 个模块 rgctx 表被就地损坏 | 无法还原（1..255 全枚举验证），置零 |
| 5 | `ForceVersion` 写 29.1 会让 dumper 用错基线 | 必须写 `29.0`，让它自走 29→29.1 得到正确 `0xF554420` |

### 3. 第 3 点的客观判据（本轮关键突破）

```
stride=36 时, methods 表 388,066 条记录:
    nameIndex     ∈ [0, stringSize)   100.0% 合法
    declaringType ∈ [0, 47503)        100.0% 合法
    解出的名字: "get_msg_type" / ".ctor" / "Equals"
    declaringType: "<>f__AnonymousType0`2"
    前 5 万条里 99.8% 是合法标识符

stride=56 (官方布局) 时:
    249,471 条, 只有 61.2% 合法, 大量空串/半截串
```

## 五、`.so` 第二层加密（定案）

```python
KEY, PERIOD, PHASE, WINDOW = 0x6F, 0x10000, 0x3000, 0x4000
mask = ((i % PERIOD) >= PHASE) & ((i % PERIOD) < PHASE + WINDOW)
data[mask] ^= KEY          # 仅作用于检出密文的块
                           # 实测范围 file [0x2D50000, 0x3B50000)
```

**判据（客观可复现）**：明文小整数 `0x00000002` 异或后是 `0x6F6F6F6D`，
所以密文 DWORD 的**高 16 位恒为 `0x6F6F`**。统计这些 DWORD 的 `位置 mod 0x10000`：

```
mod [0x3000, 0x7000)   每桶 ~30,400   ← 密文
mod 其它位置           每桶 1~8        ← 明文（统计噪声）
```

对比 `global-metadata.dat`：`key=0x66, phase=0x1000, window=0x4000`
—— **同一套加固器，不同落点**。

## 六、模拟器实测结论（本轮新增）

### 结论：**能启动，但跑不完**

游戏在 Android 模拟器上启动到：
```

```
然后崩在：
```
F ndk_translation: Guest call didn't restore sp: expected ... actual ...
F libc    : Fatal signal 6 (SIGABRT)
```

**崩溃栈完全在 `libndk_translation.so` 内部**（Google 的 ARM→x86 转译层），
调用链：`RunGuestThread → GuestCall::RunResInt64 → RunGuestCall → ExecuteGuestCall → __android_log_assert → abort`。
**没有一帧在游戏代码里**。

### 为什么

| 事实 | 说明 |
|---|---|
| 主机是 **Intel i5-1135G7 (x86_64)** | 不是 Apple Silicon |
| 游戏的 APK **只有 `arm64-v8a` / `armeabi-v7a`** | 没有 x86/x86_64 库 |
| AOSP 模拟器**拒绝在 x86_64 主机跑 arm64 镜像** | `Avd's CPU Architecture 'arm64' is not supported on x86_64 host` |
| 唯一路径 = x86_64 镜像 + `ndk_translation` 转译 | 该转译层对大型 Unity IL2CPP 支持不完善 |

### ★ v4 补充：为什么是"库根本没映射"，不是"Frida 看不到"

用 `tools\a_boot_trace.py`（**主机侧 adb 轮询 `/proc/<pid>/maps`**，完全绕过 Frida）实测：

```
  t(s)      pid  maps行  已映射的 .so
   0.0     8640    2481  libtprt.so,libtersafe2.so
   3.6     8640    2641  +libnative-lib.so
  21.5     8640  进程已退出
=== arm64 库首次出现时刻 ===
     0.0s  libtprt.so / libtersafe2.so   （ACE 加固壳）
     3.6s  libnative-lib.so
```

**`libil2cpp.so` / `libunity.so` / `libxlua.so` 直到进程退出都没出现在 maps 里。**
崩溃发生在 ACE 自己的 guest 调用（`RunGuestThread → GuestCall::RunResInt64 → ExecuteGuestCall → abort`），
**还没轮到 Unity 引擎加载**。

→ 所以 v3 那条「Frida 枚举不到 arm64 模块，需自己解析 maps」的说法要更正：
**不是枚举范围问题，而是这个库从未被 dlopen**。真机上这条限制不存在。

对照实验见 §十三（零内容改动的原包重签后崩溃**完全一样**，证明与 APK 是否被改无关）。

## 七、踩过的坑（完整版）

**v1 的 7 条**：中文路径 aapt2 失败（须 `subst X: D:\元气骑士mod`）、Android 11+ scoped storage
（gadget 用 `listen` 模式）、gadget 版本须严格一致、`on_load: wait` 阻塞启动线程、
JS 主线程不能长循环、按字节扫内存太慢（用 `Uint32Array`）、临时脚本归 `tools/`。

**本轮的 16 条新增**：

8. `ERROR: This file may be protected.` 不是错误，只要 `DT_INIT` 存在就打
9. `MapVATR` 用 `p_memsz` 且 `<=` 闭区间判边界 → 越界地址静默映射到错误偏移
10. `rgctxRanges` / `rgctxs` **每项 12 字节**（不是 24）
11. `.so` 的 `vaddr-offset` **每段不同**（0/0x4000/0x8000/0xC000），必须逐段映射
12. `.rela.dyn` 对同一目标可能有重复条目，**必须按目标地址排序后写**（后者覆盖前者）
13. `genericMethodTable` 的 `gmi==i && mi==i+1` 规律可当**验证 oracle**
14. **不能对已重定位的 `.data.rel.ro` 再做异或解密**
15. `Il2CppDecompiler.Decompile` 是**每个 image 一个 try/catch** → 一处异常丢掉整个 image
16. `DumpMethod: true` 会因方法指针索引越界大幅降覆盖（47503 → 521）
17. 改 `moduleName` 指针必须**同步改 `.rela.dyn` 的 addend**，否则 dumper 重定位时覆盖回原值
18. `ForceVersion` 写 `29.1` 会直接用 `codeRegistration-0x10` 的错误基线；写 `29.0` 才会自纠
19. PowerShell 的 **`$PID` 是只读自动变量**，脚本里别用它当普通变量名
20. AOSP 模拟器**不支持在 x86_64 主机跑 arm64 镜像**（前端直接拒绝）
21. `ndk_translation` 跑大型 Unity IL2CPP 会在 `ExecuteGuestCall` 处 `abort`
22. Frida 在 `ndk_translation` 进程里**枚举不到 arm64 模块** —— ★v4 更正：根本原因是
    **arm64 库从未被映射**（崩溃发生在 ACE 阶段），不是枚举范围问题。见 §六
23. `robocopy /MOVE` 完成后源目录会消失，第二次跑会报 `ERROR 2`（正常，不是失败）

**v4 新增 12 条（mod 打包链 + Frida 17）**：

24. **`zipfile.ZipInfo.extra` 会丢弃 zipalign 的纯 0 填充** —— 原包 `config.ab` 的 extra 是
    `b'\x00\x00'`（不是合法 extra 记录）。用 zipfile 算 `data_off` 会少算 2 字节，
    抽出来的文件头部会变成 `00 00 UnityFS` 而不是 `UnityFS`。必须自己解析 raw local header
25. **`mini_repack.py` 用 `zout.writestr` 会重算 local header 长度** → 后面 6251 个条目偏移全变，zipalign 失效
26. **替换 STORED 条目时必须保持 `data_off` 不变**。正确做法：extra 原样不动，把"新数据变小"
    产生的空隙作为**数据尾部零填充**写在该条目数据之后（同时保持整段长度不变，后续条目偏移也不变）。
    实测这样 `data_off` 变化条目 = 0
27. **`UnityPy 1.25.4` 的 `TextAsset.m_Script` 是 `str`**，直接赋 `bytes` 会在
    `write_aligned_string` 抛 `AttributeError: 'bytes' object has no attribute 'encode'`。
    用 `.decode('utf-8','surrogateescape')` 往返
28. **`BundleFile.save()` 的参数名是 `packer` 不是 `pack`**（docstring 里写的是 pack）
29. **`save(packer='lz4')` 会重压缩** → 产物比原包小 9555 字节。用 `packer='original'` 保持原
    dataflags(579) 与原压缩块结构
30. **`File.readAllText` 才是 Frida 17 读 maps 的方法**，`new File(p,'r').readAsText()` 会抛 `not a function`
31. **Frida 17 移除了 `Module.findExportByName` 静态方法**，要用 `Process.getModuleByName(so).findExportByName()`
32. **PowerShell 5.1 的 .ps1 必须带 UTF-8 BOM**，否则中文注释会导致列号错位、报一堆假语法错
33. **PowerShell 参数名不能叫 `$Args`**（自动变量）
34. **`split_lines()` 在"文件以换行结尾"时会多出一个空段** → 追加行前必须先丢掉尾部空段，
    否则会多插一个空行
35. **v1 存档那套 `t(i)=((i%15)*(i%5))%92` 与配置表无关**；实测 `weapons_drop` / `characters`
    都是**纯第 1 层异或**（`decode_full == xor_stream`，diff 0 字节），可以自由增删行
36. **`zipalign -c` 非 verbose 成功时不打印任何东西**，只返回 rc=0；
    `"Verification succesful"` 只在 `-v` 时出现（官方原文拼写就是少一个 s）→ 校验必须固定加 `-v`
37. **改 bundle 会连带影响 4 处旁路元数据** → 让产物**等长**即可全部规避，不需要逐个重算（见 §13.5）
38. **UnityFS 块标志 `0x41`（低位=1）实际是 LZ4** —— 不能只信 `flags & 0x3F`，
    对 (1,2,3) 都要试
39. **`File.readAllText` 才是 Frida 17 读 maps 的方法**（`new File(p,'r').readAsText()` 会抛错）
40. **`adb install` 的增量安装（Incremental Install）会改变验证包的字节布局** ——
    不能用「装完再 pull 出来比对整包哈希」的方式验证，必须按 raw local header 算 `data_off` 精确 dd 抽取

## 八、已知残留问题

### 1. 方法体 RVA（`methodPointers`）
`methodPointers` 数组指向 `il2cpp` 段（`0x62329E8`），不是 `.text`，且大量为 0。
这是 IL2CPP 的**方法索引 → 未解析 thunk**，需要运行时 `il2cpp_codegen_initialize_method` 填充。
→ 所以 `DumpMethod: false`。要补需**真机 + Frida**。

### 2. 22 个模块的 rgctx 表

`ICSharpCode.SharpZipLib` / `IFix.Core` / `Microsoft.Extensions.{Logging,Options,Primitives}.dll` /

`UnityEngine.UIElementsModule` / `UnityEngine.UI` / `Unity.Burst` /
`Unity.Collections.LowLevel.ILSupport` / `System.Threading.Channels` / `System.Xml.Linq` 等。

### 3. `genericMethodTable`
311,429 条，位于 `0x3500E0C`（**在加密窗口外**），是明文区的就地损坏。
全表只有 24 条满足 `gmi==i && mi==i+1`。已置 `count=0`。

### 4. 6 个模块名重复

### 13.5 ★ 旁路元数据风险（真机安全的最后一道坎）

改 bundle 会连带影响 **4 处**间接记录，任何一处被引擎校验都会让 mod 在真机上失败：

| # | 位置 | 内容 | 结论 |
|---|---|---|---|
| 1 | `_AssetBundleSize.txt` | `"config":211130` | `UISplash.GetAssetBundleSize` 读它显示总大小，错误非致命 |
| 2 | `config.manifest` 顶部 | `CRC: 2900757099` | 穷举 3 算法 × 8 切片 × 80 包配对**全不命中** → 不是内容哈希 |
| 3 | `config.manifest` | `AssetFileHash: e99bb14d…` | 与运行时 `AssetBundles.ab` 里 config 的 `AssetBundleHash` **同一个值** |
| 4 | `config.ab` 内 UnityFS | `uncompressedDataHash` = **16 个 0 字节** | Unity 这个 build **关掉了** bundle 内容哈希校验 |

**解决办法不是逐个重算，而是让新 bundle 与原 bundle 逐字节等长：**

```
UnityFS 布局（本包 flags=0x243，BlocksInfoAtTheEnd 未置位）
  [0,64)      header
  [64,130)    blocksInfo（LZ4，cs=66 us=91）
  [130,211116) 块数据（按 compressedSize 顺序读）
  尾部字节任意长都永不参与解析 → 可以安全补零
```

`a_build_ab.py` 现在会自动补零：**211130 → 211130，长度完全一致**。
于是 1/2/3 三处元数据全部仍然有效，manifest 不用改、`_AssetBundleSize.txt` 不用改。
而且该条目在 zip 里是 STORED（csize == usize），连 APK 条目长度都不用变。

验证输出：
```
[info] bundle 长度：原 211130 → 新 211130  ✓ 等长（所有旁路元数据仍然一致）
[ok ] _AssetBundleSize.txt: config=211130  vs 实际 211130
[info] UnityFS uncompressedDataHash = 0000…0000  （全 0 = 引擎未启用该哈希校验）
```

## 十五、★ v5 真机攻防全记录（本会话，最重要的新章节）

### 15.0 一句话结论

**数值 mod 的唯一拦路虎是「热更新强制覆盖」：游戏启动必须联网拉清单，清单里 config.ab 的 md5
与官方一致，我们改的包 md5 不同 → 下载官方版覆盖 → 数值永远是原版。
所有无 root 的网络层绕过（代理/DNS/改 metadata/改 .so）全部实测封死。**

### 15.1 攻防时间线（每一条都是真机实测）

| # | 实验 | 结果 | 结论 |
|---|---|---|---|
| 1 | 原包重签（零改动） | ✅ 存活 50s+ | 重签本身不触发校验 |
| 2 | config.ab 改 1 字节 | ❌ ~10s 静默退出 | 存在完整性校验 |
| 3 | config.ab 载荷同、仅换压缩 | ❌ ~4s 退出 | 校验的是**内容**不是结构 |
| 4 | 新增无害文件 dummy.bin | ✅ 存活 52s+ | **新增条目不校验** |
| 5 | **CRC32 碰撞**（内容改、CRC 同） | ✅ **存活并进关卡** | 校验是 **CRC 级**，可绕过 |
| 6 | 全角色 HP 改 9/99/999 + CRC 碰撞 | ✅ 进关卡，但画面 6/6/180 | **数值没生效** → 另有覆盖源 |
| 7 | 设备抽包比对 | md5 = 我们改的包 | 设备上确实是改包，问题不在装机 |

| 18 | 官方原包全新安装 | ✅ 正常启动到登录界面 | 之前秒退是旧数据残留，**非风控** |

### 15.2 根因链（定论）

```
我们改的 config.ab (md5 a6237d31)
    ≠ 热更清单里的 config.ab md5 (f41a3175 = 官方原版)
        → 游戏启动拉清单 → 检测本地与清单不一致
            → 从 cdn.chillyroom.com 下载官方 config.ab 覆盖
                → 运行时读热更目录 → 数值永远原版 6/6/180
断网 → 清单拉不到 → 卡"热更新加载失败"（硬门槛，无 fallback 到 APK 内配置）
```

dump.cs 铁证：
- `HotUpdateManager.RemoteUrl = "http://cdn.chillyroom.com/game/soulknight/hot_update"`（明文 HTTP！）
- `HotUpdateManager.HotUpdateFileDirName = "data"`；清单名 `hot_update_manifest.json`
- 热更文件落地 `/data/data/<pkg>/files/`（内部存储，无 root 读不到；`android:allowBackup=0` 堵死 adb backup）

### 路线 A：红手指云手机（推荐，用户手机上已装 RedFingerApp）

云手机通常带 root 或可一键 root。步骤：

1. 打开红手指 App → 创建/租一台云手机（Android 云机）
2. 装我们的 `work\isolate\sl_crcequal.apk`（CRC 碰撞改数值版）
3. 云手机内确认 root（`adb shell su` 或 Magisk 提示）
4. **有 root 后的三种打法（任选）**：
   - a) 直接读 `/data/data/com.ChillyRoom.DungeonShooter/files/` 找到热更目录，**把我们的 config.ab 换成热更落地文件**（改完 md5 与清单不符？→ 见 b）

   - c) 装官方包 → 断网 → 用 §15.2 的"签名错误弹窗 fallback"尝试进游戏（云手机上试，不碰真机）

### 路线 B：手机热点做网关（真机可做，体验差）

3. PC 跑 forge 服务器（8080）+ HTTP 80 端口伪造 CDN
4. 游戏热更请求 → PC → 伪造清单（config.ab md5=改包值）→ 游戏认为"已最新"→ 用 APK 内改版
